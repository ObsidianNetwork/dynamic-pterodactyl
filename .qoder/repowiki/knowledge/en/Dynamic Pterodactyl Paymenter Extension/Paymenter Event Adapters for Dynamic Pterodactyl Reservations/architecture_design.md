Listeners/ contains four one-method adapters, each implementing a `handle(Event $event)` entry point bound to a Paymenter core event (`App\Events\CartItem\Created|Deleted`, `App\Events\Invoice\Paid`, `App\Events\Service\Created`). Each listener resolves `ReservationService` via the container (`app(ReservationService::class)`) and delegates all business logic outward — no direct DB writes beyond reading `checkout_config` / `properties`. The flow is: CartItemCreatedListener checks for `dynamic_slider` config options, extracts memory/cpu/disk values and a location ID, then creates a reservation and stores its token in `checkout_config`; CartItemDeletedListener cancels the reservation unless the cart item was already consumed by checkout (checked via Service properties); InvoicePaidListener re-verifies availability through `ResourceCalculationService::verifyAvailability` before confirming the reservation via `ReservationService::confirm`, emitting shortfall alerts on failure; ServiceCreatedListener is a no-op logger that only records services that arrived with a reservation token. Events/ defines a single domain event `AlertDeliveryFailed` (using Laravel's `Dispatchable` + `SerializesModels`) carrying an `AlertDeliveryLog` model, used as an outbox-style signal when alert delivery fails. Dependency direction is strictly inward toward Services/ and outward-only via logging; listeners never return HTTP responses or call controllers.
